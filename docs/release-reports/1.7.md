## Highlights

1. **did:peer:4 for new relationships.** A TypeScript port of DIF's did-peer-4 (no npm package existed). Existing did:peer:2 relationships keep working.
2. **Portable subtree move.** Export a pico subtree (rulesets, entity state, channels, schedules, identity snapshots) from one engine and import it on another with `io.picolabs.portable_subtree`.
3. **Relationships survive the move.** DID rotation tells cross-engine peers where the pico went; community links are kept on export.
4. **Single-ruleset state export.** `ctx:exportRulesetState` / `ctx:importRulesetState` produce encrypted blobs.
5. **Flush reinstalls.** Flushing an installed ruleset in the developer UI now reinstalls it, so the new KRL takes effect without a separate Install.

## Why it matters

- **Picos aren't tied to the engine they were born on.** That's the point of a persistent compute object: identity and relationships outlive the host. 1.6 gave picos DIDs; 1.7 made them portable.
- **Standards-grade peer DIDs.** did:peer:4 is the current DIF method, which matters for interop with other DIDComm implementations.

## What changed for identity

| | 1.6 | 1.7 |
|---|---|---|
| Peer DID method for new relationships | did:peer:2 | did:peer:4 |
| Moving a pico to another engine | Not possible | Export and import a subtree; DID rotation updates peers |
| Legacy `io.picolabs.did-o` | Deprecated | Retired from the move paths |
| Ruleset state backup | Not available | Encrypted per-ruleset export and import |

## Upgrade

- New DID-based relationships use did:peer:4; existing ones are unchanged.
- After upgrading, flush `io.picolabs.manifold_pico` on each Manifold app pico, not only on the mesh root.
- The importing mesh must provide any platform services the subtree relied on (for example a Manifold app under a Manifold parent).
