# Pico Engine 1.8 — Mesh API + security (plan)

**Status:** plan (October 15, 2026)  
**Requires:** pico-framework **`^0.8.2`** (policy ceiling; publish before engine 1.8)

---

## Theme

Make a pico's **surface machine-readable**, make its **authority correct**, and **expose both to agents** — the ones that build with picos (Claude Code, Cursor) and the ones that operate a mesh (harnesses, see [`agent-harness-on-mesh.md`](../design/agent-harness-on-mesh.md)).

Three engine pieces form one dependency chain, plus a developer-loop track that has no prerequisites and ships first:

```
annotations  →  channel policy fix  →  built-in MCP server (mesh tools)
                                        ↑
agent readiness (dev MCP tools, krl check, CLAUDE.md, llms.txt, OpenAPI) ─┘
```

**Why together:** MCP tools generated from `picoSchema()` are only safe if the channel that scopes them cannot be widened by a leaked ECI. Schema says *what* a pico can do; policy says *who* may do it; the MCP server is the first consumer that needs both to be true at once.

**Deferred to 1.9+:** selective logging & replay on schema `logged` flags, pico mirrors, local LLM per pico (`MEMORY.md` roadmap §2, §3, §8 — all depend on 1.8 schema).

#### Deployment: local vs hosted (e.g. AWS)

The built-in MCP server is **one package with two modes**; they are **not** both exposed the same way in production.

| Where you run | What agents use | What is exposed on the network |
|---------------|-----------------|--------------------------------|
| **Local dev** (laptop, `npm start`, `PICO_ENGINE_HOME=~/.pico-engine`) | **Dev MCP** — `pico-engine mcp --stdio` in Cursor / Claude Code / other MCP clients | **Nothing new.** Stdio talks to the **local** engine process (same mesh as the UI). Do **not** put dev MCP on a load balancer or Fargate task. |
| **Hosted** (AWS ECS/Fargate, Docker on a VPS, etc.) | **HTTPS engine** as today — UI (passkey), `/sky/*`, OAuth integrators; **mesh MCP** when shipped | **HTTP(S) on `PORT`** (UI + Sky + OAuth). **Mesh MCP** is Streamable HTTP on that engine, **not** stdio dev tools. |

**Local developer loop.** Set `PICO_ENGINE_HOME` (and `PORT` / `PICO_ENGINE_BASE_URL` if needed) the same way for `npm start` and for the MCP subprocess. The agent sees the **whole forest on that engine instance** — install, flush, `eval_krl`, Testing-equivalent raise/query — the same posture as the owner UI channel, not a single OAuth-scoped ECI.

**Hosted mesh (AWS and similar).** Persistent state lives under `PICO_ENGINE_HOME` (e.g. EFS at `/var/pico-image`); the public URL is `PICO_ENGINE_BASE_URL` (HTTPS behind ALB, Cloudflare, nginx, etc.). Operators use the **browser UI** with passkeys. Automations and integrators use **OAuth** and **narrow channels** (client credentials or authorization code), same as 1.5+.

**Mesh MCP on a hosted engine** (operator / harness, not ruleset authoring):

- **Auth:** OAuth **bearer token scoped to one channel ECI** (same family as `/sky/*`); not anonymous MCP on the internet.
- **Tools:** Generated from **`channelSchema(caller_eci)`** — annotated events and queries only; no dev toolbox (`install_ruleset`, forest-wide `list_picos`, owner `eval_krl`, …).
- **Policy:** Channel event/query policy plus §2 fixes (deny beats permit, ceiling, wildcards requiring validated caller identity) so a leaked ECI cannot be widened to match what MCP needs.
- **Owner-only surfaces stay owner-only:** KRL console and `eval_krl` remain **UI channel + local dev MCP**, not discovery, generic OAuth app channels, or mesh MCP.

**Production env vars** (hosted; see also `packages/pico-engine/README.md` § Containers / Fargate):

| Variable | Hosted recommendation |
|----------|------------------------|
| `PICO_ENGINE_BASE_URL` | Public **HTTPS** origin (required for passkeys and did:webvh) |
| `PICO_ENGINE_ALLOW_SELF_SIGNUP` | Off unless you intend open registration |
| `PICO_ENGINE_ALLOW_LOCALHOST_C` | `"0"` — do not treat `/c/*` as localhost-trusted on AWS |
| `PICO_ENGINE_LOG_FILE` | `stdout` on Fargate (CloudWatch); avoid heavy log files on EFS |

**Blog shorthand:** *Developer MCP connects your IDE to the **local** mesh under `PICO_ENGINE_HOME`. On AWS you run the **HTTPS engine**; agents that act on the **live** mesh use **OAuth-scoped mesh MCP**, not stdio dev MCP.*

#### Dev MCP usage (local)

1. Start the engine (`npm start` at repo root, or `pico-engine`) with the same `PICO_ENGINE_HOME` you use in the browser.
2. In another process (or Cursor MCP config), run **`pico-engine mcp --stdio`**. It talks HTTP to `PICO_ENGINE_BASE_URL` (default `http://localhost:3000`).
3. **`GET /api/dev/local`** (localhost only) returns `rootUiEci` so the MCP server can resolve the UI channel without a passkey. Override with **`PICO_ENGINE_UI_ECI`** when the engine requires auth sessions on `/c/*`.

Operator settings live in **`~/.config/pico-engine/config.json`** (see `packages/pico-engine/config.example.json`), not in the repo. **Multiple engines:** one config file per process (`config.instances.example/`, `docker/config/`); `pico-engine -c <path>` or `PICO_ENGINE_CONFIG`. Point MCP at the config for the engine you want:

Example Cursor MCP config (`.cursor/mcp.json`):

```json
{
  "mcpServers": {
    "pico-engine": {
      "command": "node",
      "args": ["/absolute/path/to/pico-engine/packages/pico-engine/dist/cli.js", "mcp", "--stdio"],
      "env": {
        "PICO_ENGINE_CONFIG": "/Users/you/.config/pico-engine/config.json"
      }
    }
  }
}
```

After `npm run build`, you can also use the `pico-engine` binary on your `PATH`. Tools: `engine_status`, `validate_krl`, `eval_krl`, `query`, `raise_event`, `list_picos`, `pico_schema`, `ruleset_schema`, `list_channels`, `tail_events`, `install_ruleset`, `flush_ruleset`, `create_pico`, `delete_pico`, `create_channel`.

### 4. Agent readiness (developer loop)

| Item | Notes |
|------|-------|
| **`krl` CLI** | `krl check <file>` — parse + compile + schema lint, errors with line/col and a hint; `krl fmt` via `krl-generator`; `krl schema <file>` prints schema JSON. Lives in `krl-compiler` bin (today: stdin→stdout only, no diagnostics mode) |
| **KRL console** | Evaluate a KRL **expression** in the context of an installed ruleset on a pico: its `global` functions and constants, its module aliases, and its `ent:` variables (`ent:established` in `io.picolabs.subscription`). For inspecting state, which the opt-in annotations deliberately don't document, and for trying an expression against real state before writing it into a rule. **Read-only by construction:** the input is compiled as an expression and run in **query context**, like a shared function, so it can't assign `ent:` (postlude only) or run actions (action block only); it runs as a transaction on the pico's queue, so it sees consistent state. Shared functions that change state despite being queries (e.g. oauth `createChannelSecret`) remain callable, which is acceptable for an owner-only console. **Owner only:** UI channel with a passkey session, and the dev MCP server against a local engine; never discovery, OAuth, or app channels. Every evaluation is logged (visible in the Logging tab). Surfaces: `ctx:evalInRuleset(rid, expr)` (engine; not for app rulesets), a console in the Rulesets tab next to **Docs**, and the dev MCP tool `eval_krl(eci, rid, expression)`. Compiler work: compile a lone expression against an installed ruleset's scope |
| **Doctests** (stretch) | Run each `@example` as a test: install the ruleset on an isolated test engine, send the example, require the annotated rule to be *selected and fired* (query examples: run without error). Examples with placeholders (`"<eci>"`) are skipped until fixtures exist. `krl doctest <file>` plus a CI job over the bundled rulesets. Design: [`live-pico-ui.md`](../design/live-pico-ui.md#doctests) |
| **Parser diagnostics** | Targeted messages for the known traps: stray character after `meta { }` (today: generic `Unsupported characters :L:C` — say *what* was unexpected and *where in the structure*), chained `ent:x{a}{b} :=` (want composite path), second postlude, action-block `else`, second action block, `event:send` inside `fired`, `pre` re-binding |
| **Install-failure visibility** | **Root cause of "stray character silently prevents registration" (manifold-api MEMORY.md):** the parser rejects it fine; the failure is swallowed downstream. (a) `PicoEngineCore.onFrameworkEvent` logs `txnError` at **error**, not debug, with `picoId`, `rid`, rule name, and the compiler error incl. location. (b) New `ctx:validate(url \| krl)` → `{ ok, rid, errors[], warnings[] }` (same diagnostics `krl check` prints). (c) Wrangler `install_ruleset_absolutely` validates in `pre`, gates the action on `ok`, and raises **`wrangler ruleset_install_failed`** `{url, rid, errors}` in the `else` postlude — `ruleset_installed` only on success. (d) `ctx:flush` same treatment: `wrangler ruleset_flush_failed`. (e) UI Install/Flush surface the error with location. (f) Stored `compiler.warnings` surfaced via `wrangler:rulesetWarnings(rid)` instead of only persisted |
| **Rule outcome reporting** | Event responses (`/sky/event`; and a `wrangler rule_outcome`-style event for `event:send`, where there is no reply path) report, per **annotated** rule whose entry event arrived: `fired`, `not_fired: condition false`, or `not_selected` (attr pattern / `where` didn't match), alongside directives and eid. Engine already tracks selection and firing; this surfaces it. Replaces both the dropped `@guard` annotation and event-attr validation; gives agents and the Testing tab an answer instead of silence |
| **`CLAUDE.md` + `AGENTS.md`** | Repo root: layering rule, layout, commands, KRL conventions, where docs live. Same for `manifold-api`, `sensor-network`, `MCPforEXP` |
| **`llms.txt`** | Served from `packages/pico-engine/public/docs/` (`llms.txt` index + `llms-full.txt` concatenation of pico, pico-engine, KRL manual) |
| **OpenAPI** | Spec for `/sky/event`, `/sky/cloud`, `/c/*`, auth/OAuth endpoints; published under `public/docs/` and referenced from `llms.txt` |
| **One-line start** | `npx pico-engine` and `docker run` both documented at the top of the README with no UI steps required to reach a working root pico |
| **Channel policy audit (user-facing)** | Summarize [`channel-policy-audit-2026-10.md`](../design/channel-policy-audit-2026-10.md) in `1.8.0.md` release notes: permissive root default, opt-in wildcard Sky lock, known Manifold wide channels |

## Exit criteria

| # | Check |
|---|-------|
| 1 | A fresh Claude Code session with only `CLAUDE.md` and `pico-engine mcp` can start an engine, write a ruleset that passes `krl check`, install it, raise an event, and query — without opening the wiki |
| 2 | `rulesetSchema(rid)` returns the annotated operations and queries for one RID, and the Testing tab renders from it; `picoSchema()` on a pico with wrangler + PDS + an app RS returns one merged, deduped, typed aggregate of those ruleset schemas |
| 3 | Policy tests: deny beats permit; `createChannel` above the ceiling is rejected; wildcard channel without caller identity is refused |
| 4 | Mesh MCP tool list for a channel equals `channelSchema(caller_eci)`; a call outside it is refused with a policy error, not a 500 |
| 5 | Eval baseline recorded (tasks, pass rate with/without skill) |
| 6 | Installing a ruleset with a stray character after `meta { }` (via `raise wrangler event "install_ruleset_request"`, not HTTP) produces an **error**-level log line with `rid` and `:line:col`, a `wrangler ruleset_install_failed` event the parent can select on, and no `ruleset_installed`; the Testing/Rulesets UI shows the same message |
| 7 | Sending `manifold create_thing` when Manifold is at `max_picos` returns a response naming `create_thing` as *selected, not fired (condition false)*; discovery lists `canCreateThing` as its precheck without any annotation |
| 8 | In the UI console on a pico with `io.picolabs.subscription`, `ent:established.length()` and `established("Tx_role", "manifold_thing")` evaluate in that ruleset's context; an input containing `ent:x := 1` or an action is rejected at compile time; the same works through the dev MCP tool `eval_krl`; each evaluation appears in the Logging tab |
| 9 | An event sent from the Testing tab appears in history with its outcome; saving it, then opening the same pico in a different browser, shows the saved request; after a portable export and import of the pico, the saved request is still there; "Copy as `@example`" yields a line that passes `krl-check` when pasted into the ruleset's annotation; a `password` attr is masked in history |

## Open questions

| Question | Notes |
|----------|-------|
| Inline KRL install from the dev MCP server | Rulesets are URLs today. Options: local file-serving registry (`RulesetRegistryLoaderFs`), `data:` URLs, or a dev-only `/rulesets/inline` endpoint. Dev-only either way |
| Ceiling without domain vocabulary | Parent-sets-ceiling-at-creation keeps the engine agnostic; confirm Manifold can express owner/thing/community ceilings that way |
| Schema conflicts | Resolved in design: type mismatch → `conflicts[]`; never block install. Engine merge (not wrangler) |
| Tool naming | `domain_type` for events and `rid_fn` for queries is unambiguous but long; MCP clients truncate at ~64 chars — may need a per-RID alias |
| Package boundary | `pico-engine mcp` subcommand vs. standalone `@picolabs/mcp`; subcommand wins for dev UX, standalone for harness deployments — likely both from one package |
| Where the skill lives | `Picolab/krl-skill` vs. inside `pico-engine`; separate repo keeps the engine release independent of skill iteration |
